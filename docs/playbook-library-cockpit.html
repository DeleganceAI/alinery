Proposal · Playbook library

One library. Every playbook shows where it came from, where it lives, and whether it matches the community copy.

Today the page splits Local from Community, counts downloads twice, lists other people's downloads under My Playbooks, and matches your publications by key alone. This proposal removes the split. There is one list, one status vocabulary, and one inspector that draws each playbook's lineage. Click around: the rail, rows and cards are live with example data. Double-click a row, or press Open, for the ring detail view.

The model

Three questions, answered on every row

Origin

Where did it come from?

Alinery (built in), Mine (made or copied here), @label (downloaded from someone), Team (committed in the repo's alinery/playbooks, read-only). Origin never changes. Copying any of them makes a new Mine.

Range

Where does it live?

This repo or All repos. Today's "Repository" and "Global" scopes, named by what they mean. A download asks which, instead of always landing in the repo.

Link

Does it match the community?

Two possible links, never confused: upstream (the listing you downloaded from) and your listing (the one you publish). The status column shows whichever link exists, and the inspector draws both.

Where things go

The rail replaces tabs, filter chips and the featured column

  • Library groups by origin: All, Starred, Mine, Downloaded, Team, Alinery. A download counts once.
  • Signals appear only when non-zero: updates waiting, changes not published, edited copies with an update, withdrawn listings. This is the one place to look after time away.
  • Community holds Explore (featured strip, then the catalog) and Your listings. A community card you already have shows the same status as its library row.
  • Search is one command line. Plain text searches the library; @ searches the community. This drops the duplicate search box and the "Starred only" checkbox.
  • The inspector replaces the Featured column. It shows the playbook's ring, the lineage track, its steps and the actions for the current state. Open (or double-click a row) leads to the detail view.
Look and feel

Cockpit, built from the site's own parts

  • The alinery.ai palette: void black, warm-white hairlines, periwinkle as the only action colour. Status LEDs carry state, so colour never decorates.
  • Geist Mono, uppercase, for instrument labels; Sora for names; Geist for reading.
  • Ring fingerprint: each row and card draws its playbook as a small ring, the same one alinery.ai's library cards use. Amber nodes wait for you and a green dashed arc loops, so a one-shot, a loop and a seven-step pipeline look different before you open them.
  • A dense manifest, not cards. Cards only in Explore, where browsing is the point.
  • Light theme keeps the same structure and swaps the tokens. The cockpit comes from the type and the lines, not from darkness.
The detail view

The ring from alinery.ai replaces the canvas

Open a playbook and it draws as the ring from the homepage hero (website PR 163). Hover a step, or its chip in the inspector, and the centre reads Step 3 of 7, its name, whether it waits for you, fans out or moves on by itself, and the first lines of its prompt. The hover is sticky, so the readout stays on the last step you visited. Source sits beside Ring as the editor.

The ring fits any pane with no panning, because each node's position comes straight from its index. The loop that most playbooks end with becomes the arc that closes the circle, which the layered canvas never showed. The built-in rings in this mockup come from the real playbook files.

There is no animation. The app's own ring branch removed its timed demo on purpose, and in an editor the ring answers hover and click instead. The website's runner dots can stay on the homepage.

What changes in the code

Fixes the redesign depends on

  1. Link publications by id, not key. Record your listing's id beside the local playbook (a published record in community-imports.toml). This stops My Playbooks claiming other people's downloads and stops a global and a repo copy sharing one listing (Playbooks.tsx publishedRows).
  2. "Changes not published" from hashes. Compare the local file's sha256 with the listing's bodySha256, which the server already returns and the app ignores.
  3. Use the daemon's locallyEdited. sync/community.ts drops it today, and the page falls back to an in-memory flag that forgets on reload.
  4. Handle every reply. Give already_downloaded and "remote version is lower" real wording, and format updatedAt.
  1. Download asks for a range. communityImports.ts always writes repo scope; allow All repos.
  2. Team as its own origin. The catalog already knows committed claims (committedClaims). Expose that so they read as read-only instead of failing on save.
  3. Step graph on catalog rows for the row fingerprint. The detail view already has the full definition, so only the list needs this, and it's a proto field (protocol bump). Until then a row draws a plain ring of its step count, as the website does.
  4. Unpublish and restore. Wire the server's existing DELETE, and add Show hidden for removed built-ins (the tombstone has no undo today).
